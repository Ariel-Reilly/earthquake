# DisasterGuard 信息架构重构方案

> **目标**: 解决功能呈现扁平、业务逻辑杂乱的问题，建立层次清晰、符合灾害管理工作流的信息架构

---

## 📊 现状诊断

### 当前问题

#### 1. **导航过载**
- **6 大分组，45+ 菜单项**：用户需要在 45 个菜单中找到目标功能
- **分组逻辑混乱**：
  - "灾害研判"组有 11 项（AI 任务、AI 结果、灾害事件、确认工作台、会签、现场巡检……）
  - "设备与数据"组有 8 项（设备、数据、模型混杂）
  - **问题**: 用户无法快速建立心智模型，"我要做 X，应该去哪里？"

#### 2. **工作流断裂**
- **预警处置流程**分散在 4 个地方：
  - `/dashboard/warnings` - 预警列表
  - `/dashboard/warnings/:id` - 预警详情
  - `/dashboard/emergency` - 应急事件
  - `/dashboard/resource-dispatch` - 资源调度
  - **问题**: 用户需要在 3-4 个页面之间跳转才能完成一次预警响应

#### 3. **功能定位不清**
- **"灾害事件" vs "统一事件中心" vs "应急事件"** 三者边界模糊
- **"AI 巡检任务" vs "AI 推理结果" vs "AI 综合研判"** 分散成 3 个页面，但本质是同一个工作流的不同阶段
- **"数据管理" vs "数据源接入" vs "数据同步监控" vs "数据资产目录"** 4 个页面，用户搞不清应该去哪里

#### 4. **扁平化展示**
- **OverviewPage（综合态势大屏）** 试图展示所有信息：
  - 实时气象、设备状态、灾害点、AI 评分、预警列表、统计图表……
  - **问题**: 信息密度过高，核心指标被淹没

#### 5. **重复建设**
- **3 个"详情页"模式**：
  - 灾害详情页（`HazardDetailPage.vue`）
  - 预警详情页（`WarningDetailPage.vue`）
  - 设备详情页（`DeviceDetailPage.vue`）
  - 但它们的 Tab 结构、操作按钮、数据面板高度相似，缺乏统一设计

---

## 🎯 重构目标

### 设计原则

1. **按工作流组织，而非按功能类型**
   - ❌ 不要按"AI 功能"、"数据功能"分组
   - ✅ 按"监测 → 研判 → 预警 → 处置 → 复盘"的工作流分组

2. **深度优于广度**
   - ❌ 不要把所有功能平铺在侧边栏
   - ✅ 用 Tab、抽屉、分步向导等方式聚合相关功能

3. **首屏即可操作**
   - ❌ 不要让用户点 3 次才能开始工作
   - ✅ 关键操作一键可达（顶栏"新建预警"、地图右键"派发任务"）

4. **上下文保持**
   - ❌ 不要让用户在多个页面间反复跳转
   - ✅ 在同一个上下文内完成完整工作流（预警详情页内完成确认/派发/关闭）

## 🗂️ 新信息架构

### 一级导航（顶栏横向 Tab，5 个）

```
┌──────────────────────────────────────────────────────────────────┐
│ [态势监测] [研判决策] [预警响应] [资源管理] [系统配置]           │
└──────────────────────────────────────────────────────────────────┘
```

| 一级分组 | 用户问题 | 核心页面数 |
|---------|---------|----------|
| **态势监测** | "现在情况如何?" | 2-3 个 |
| **研判决策** | "这是什么灾害?风险多大?" | 2-3 个 |
| **预警响应** | "需要通知谁?如何处置?" | 1-2 个 |
| **资源管理** | "有哪些设备/数据/人员?" | 3-4 个 |
| **系统配置** | "如何管理系统?" | 3-4 个 |

  - ❌ 删除"设备健康度详情"（移到 `/dashboard/devices`）

#### 2.1 AI 研判工作台（/dashboard/intelligence）

**合并页面**：

- 原 `/dashboard/ai-results` - AI 推理结果

- 原 `/dashboard/damage-assessment` - 灾损评估
- 原 `/dashboard/confirmation-workbench` - 人工确认工作台

**新布局**：

```
┌──────────────────────────────────────────────────────────────────┐
│ Tab: [●待研判 (7)] [○AI 任务] [○历史研判] [○预测评估]           │
├───────────────┬──────────────────────────────────────────────────┤
│ 待研判列表    │  研判详情                                         │
│               │  ───────────────────────────────────────────────  │
│ 🤖 AI-2024... │  📸 影像对比                                      │
│ 评分: 82/100  │  [前] ──────── [后]                               │
│ 地点: 房山区  │  (并排显示变化检测结果)                           │
│ 15:30         │                                                   │
│ [认领] [转派] │  🎯 AI 分析                                       │
│               │  • 灾害类型: 滑坡（置信度 87%）                   │
│ 🤖 AI-2024... │  • 影响范围: 约 2.3 公顷                          │
│ 评分: 76/100  │  • 风险等级: 橙色                                 │
│ ...           │  • 建议措施: 立即疏散周边 500m 居民               │
│               │                                                   │
│               │  💬 人工研判                                      │
│               │  [确认为滑坡灾害]  [误报]  [需现场核实]          │
│               │  备注: ___________________________________        │
│               │         [提交研判意见]                            │
└───────────────┴──────────────────────────────────────────────────┘
```

**Tab 结构**：

1. **待研判 (默认Tab)**：AI 检测到的异常，等待人工确认
   - 左侧列表：按 AI 评分排序，显示地点、时间、评分
   - 右侧详情：影像对比 + AI 分析 + 人工研判操作

2. **AI 任务**：查看自动巡检任务的执行状态
   - 任务列表：任务名称、覆盖区域、执行频率、最近运行时间
   - 任务详情：执行日志、异常检出记录

3. **历史研判**：已确认/已忽略的研判记录
   - 支持按时间、灾害类型、处理人筛选
   - 查看研判依据与决策过程（可追溯）

4. **预测评估**：
   - 灾害预测：基于历史数据 + 气象预报，预测未来 24-72 小时可能发生的灾害
   - 灾损评估：对已发生灾害的影响范围、经济损失进行评估

**设计要点**：
- **工作流一体化**：AI 检测 → 人工研判 → 确认/忽略，全在一个页面完成
- **聚焦待办**：默认 Tab 是"待研判"，用户进来直接开始工作
- **减少冗余**：不再维护 6 个独立页面，降低维护成本

## 🎯 聚合策略详解

### ✅ 应该聚合的场景（用 Tab）

1. **同一实体的不同维度**
   - ✅ 预警详情页：[基本信息] [通知送达] [处置记录]
   - ✅ 设备管理：[设备列表] [设备地图] [OTA 升级]

2. **同一工作流的不同阶段**
   - ✅ AI 研判工作台：[待研判] [AI 任务] [历史研判] [预测评估]
   - ✅ 资源调度：[资源调度] [路径规划] [现场巡检]

3. **同一数据源的不同视图**
   - ✅ 事件中心：[全部事件] [灾害事件] [应急响应] [误报记录]
   - ✅ 数据中心：[数据总览] [数据源] [同步监控] [资产目录]

4. **同一管理域的不同配置**
   - ✅ 系统配置：[用户权限] [通知配置] [AI配置] [系统监控] [日志审计]

### ❌ 不应该聚合的场景（保持独立页面）

1. **不同的核心实体**
   - ❌ 不要把"预警"和"设备"放在同一个页面
   - ❌ 不要把"用户管理"和"数据管理"合并

2. **不同的用户角色**
   - ❌ 不要把"管理员配置"和"普通用户操作"混在一起
   - 原因：普通用户看到很多灰色的"无权限"Tab 会困惑

3. **独立的专项工具**
   - ✅ 保持独立：气象分析、地图、统计分析
   - 原因：这些是用户会长时间停留的"工作台"，不适合作为 Tab

## 📏 设计规范

### Tab 使用规范

1. **Tab 数量控制**：
   - ✅ 推荐 3-5 个 Tab
   - ⚠️ 超过 5 个时考虑二级分组或拆分页面
   - ❌ 禁止超过 7 个 Tab（人类工作记忆极限）

2. **Tab 命名规范**：
   - ✅ 使用动宾结构或名词："待研判"、"历史记录"
   - ✅ 带数字徽章："待研判 (7)"、"活跃预警 (18)"
   - ❌ 避免模糊词汇："其他"、"更多"

3. **Tab 顺序规则**：
   - **默认 Tab = 最高频使用的 Tab**
   - 按工作流顺序排列：输入 → 处理 → 输出
   - 历史/归档类 Tab 放在最后

### 抽屉 vs 弹窗 vs 新页面

| 交互方式 | 适用场景 | 示例 |
|---------|---------|------|
| **新页面** | 需要长时间停留、多步操作、复杂信息 | 预警详情页、设备详情页 |
| **抽屉（侧边）** | 需要保持上下文、快速浏览、辅助信息 | 通知抽屉、人员信息抽屉 |
| **弹窗（模态）** | 需要用户确认、填写表单、轻量操作 | 创建预警、关闭预警、删除确认 |

**禁止使用弹窗的场景**：
- ❌ 超过 5 个字段的表单（用新页面）
- ❌ 需要参考背景信息的操作（用抽屉保持上下文）
- ❌ 多步骤向导（用新页面 + 步骤条）

## 🎨 视觉设计建议

### 1. **信息层级**

  - **H1（页面标题）**: 30px, Bold
  - **H2（区块标题）**: 20px, Semibold
  - **H3（卡片标题）**: 16px, Medium

### 2. **颜色语义**
- **红色系**：高危、错误、删除操作
- **橙色系**：中危、警告
- **黄色系**：低危、提示
- **绿色系**：成功、正常状态
- **蓝色系**：信息、链接
- **莫兰迪绿（品牌色）**: 主按钮、导航高亮

### 3. **卡片设计**
- **统一圆角**: 12px（`--radius-lg`）
- **统一阴影**: `--shadow-md`（静态）/ `--shadow-hover`（悬停）
- **统一间距**: 卡片内边距 24px（`--space-lg`）
