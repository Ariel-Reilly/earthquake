## 二、致命缺陷（CRITICAL）— 必须立即修复

### CRITICAL-1 前端卫星服务直连 AI 服务，绕过认证鉴权

- **文件**：`frontend/src/services/_architecture/core/sentinelService.js`
- **位置**：第 30-39 行，`DEFAULT_AI_SERVICE_BASE`
- **问题描述**：
  ```javascript
  const DEFAULT_AI_SERVICE_BASE = (() => {
    const raw = import.meta.env.VITE_AI_SERVICE_BASE || ...
    return base + '/api/ai'
  })()
  ```
  前端 sentinelService 直接访问 `http://localhost:8001/api/ai`（Python AI 服务），完全绕过了 Java 后端网关（8080端口）。这意味着：
  1. **绕过了 JWT 认证鉴权** — 任何人都可以直接调用 AI 服务
  2. **绕过了后端的降级和容错处理**
  3. **生产环境会有跨域问题**（前端 5173 → AI 服务 8001）
  4. **与项目整体架构不一致** — 其他所有 API 都走 `/api/ai/*` 经 Java 转发
- **影响**：安全漏洞 + 架构不一致 + 生产环境不可用
- **修复方案**：在 Java 后端 `SentinelController` 中增加 `/compose`、`/jobs/{jobId}`、`/diff` 等端点，由 Java 端转发到 Python AI 服务。前端改为走 `VITE_API_BASE_URL`（即 Java 网关）。

### CRITICAL-2 Java 后端 SentinelController 只有 mock coverage 接口，无卫星合成功能

- **文件**：`backend/src/main/java/cn/disasterguard/ai/SentinelController.java`
- **位置**：第 26-134 行，整个控制器

  Java 后端的 `SentinelController` 只有一个 `GET /api/sentinel/coverage` 接口，返回纯 mock 的切片数据（第 83-130 行 `generateMockTiles`）。

  - `GET /api/ai/sentinel/diff-jobs/{jobId}` — 查询差异任务
- **影响**：前端卫星对比页面如果走后端路线会完全不可用；只能直连 AI 服务（见 CRITICAL-1），形成"为了能用而绕过安全"的恶性循环。
- **修复方案**：在 `SentinelController` 中实现上述四个端点，通过 `AiServiceClient` 或新增的 `SentinelServiceClient` 转发到 Python AI 服务。

### CRITICAL-3 卫星图返回 file:// URL，前端浏览器无法加载

- **文件**：`ai-service/app/routers/sentinel.py`
- **位置**：第 441-444 行，`_save_image_bytes_to_storage` 函数
- **问题描述**：

- **修复方案**：

  2. 确保 `SENTINEL_CDN_BASE` 默认值正确指向 `http://localhost:8001/sentinel_files`
  3. 如果走 Java 网关路线，Java 端应代理静态文件或重定向到 CDN

### CRITICAL-4 Java 异常检测接口数据格式不匹配（一维 vs 二维）

- **文件**：`backend/src/main/java/cn/disasterguard/ai/AiServiceClient.java`
- **位置**：第 110-124 行，`anomaly` 方法
- **问题描述**：
  Java 端调用异常检测时传的 `data` 是 `List<Double>`（一维数组）：
  ```java
  public AnomalyResult anomaly(String deviceCode, List<Double> data) {
      Map<String, Object> payload = Map.of("device_code", deviceCode, "data", data);
  ```
  但 Python 端 `AnomalyRequest.data` 的类型是 `List[List[float]]`（二维矩阵，每行是 5 维传感器向量）：
  ```python
  data: List[List[float]] = Field(
      description="传感器样本矩阵，每行一个样本；每行应是 5 维向量"
  )
  ```
  Pydantic 会因为类型不匹配返回 **422 Unprocessable Entity**，导致异常检测完全失败。
- **影响**：AI 实时监测的异常检测功能完全不可用
- **修复方案**：
  1. Java 端构造正确的二维数组格式（5 维传感器向量 × N 个时间步）
  2. 或 Python 端增加对一维数组的兼容（自动复制为 5 维，如注释中所说的"兼容旧格式"）

### CRITICAL-5 融合引擎评分多乘 100 倍，导致评分超出 0-100 范围

- **文件**：`ai-service/app/models/fusion_engine.py`
- **位置**：第 131 行，`fuse` 方法
- **问题描述**：
  ```python
  # 各模态 score 已经是 0-100 范围
  weighted_sum += weight * score_obj.score  # 加权后还是 0-100
  ...
  fused_score = weighted_sum / weight_sum * 100  # 又乘了 100！变成 0-10000
  ```
  `ModalScore.score` 的注释明确说是 `0-100`，但 `fuse` 方法在加权平均后又乘了 100，导致最终 `fused_score` 范围变成 `0-10000`。
  而 `LEVEL_THRESHOLDS` 的阈值（80/60/35）是按 0-100 设计的，结果几乎所有输入都会被判为 CRITICAL。
- **影响**：多模态融合评分完全错误，所有事件都是最高等级
- **修复方案**：移除 `* 100`，改为 `fused_score = weighted_sum / weight_sum`

### CRITICAL-8 红色预警 CSS 样式被错误映射为蓝色

- **文件**：`backend/src/main/java/cn/disasterguard/warning/service/WarningService.java`
- **位置**：`cssClass` 方法

### CRITICAL-10 社交媒体告警等级计算存在 -1 偏差，导致评分系统性偏低

- **文件**：`ai-service/app/models/comprehensive_model.py`
- **位置**：`score_social_media` 函数
- **问题描述**：
  ```python
  raw_alert = factors.get("social_alert_level", 0.0)
  alert_level = max(0.0, min(4.0, raw_alert - 1.0))  # 错误地 -1
  ```
  注释说"GDACS alertscore (1-5) → social_alert_level (0-4)：直接 -1 归一化"，但根据 `comprehensive.py` 的 factors 文档和 `disaster_assessment_model.py` 的定义，`social_alert_level` 的取值范围本身就是 **0-4**（0=无，4=紧急），不是 GDACS 的 1-5。
  
  如果传入 `social_alert_level=4`（紧急），代码会计算为 `4-1=3`，导致最高等级的舆情告警被降一档计算。
  
  同时 `disaster_assessment_model.py` 的 `score_social_media` 没有这个 -1 操作，两个模型对同一因子的处理不一致。
- **影响**：综合模型的社交媒体维度评分系统性偏低约 25%，舆情驱动的预警可能被漏报
- **修复方案**：移除 `raw_alert - 1.0` 中的 `-1.0`，直接使用 `raw_alert`

## 三、严重缺陷（HIGH）

### HIGH-1 前端卫星 provider 枚举值与后端不匹配

- **文件**：`frontend/src/services/_architecture/core/sentinelService.js`
- **位置**：第 49 行 JSDoc 注释和第 188 行默认值
- **问题描述**：
  前端 provider 类型声明为 `'gee'|'copernicus'`，默认值为 `'copernicus'`。
  但 Python 端支持 6 种 provider：`auto / copernicus / earth_search / usgs / gee / mock`。
  前端没有 `auto` 选项（推荐的 fallback 模式），用户只能强制走 CDSE 或 GEE，CDSE 凭证缺失时会直接失败。
- **影响**：用户体验受限，CDSE 凭证不可用时无法自动降级到公开数据源
- **修复方案**：前端扩展 provider 枚举，默认改为 `'auto'`

### HIGH-2 字符串类型因子被设为 float 0.0，语义完全丢失

- **文件**：`ai-service/app/routers/disaster_assessment.py`
- **位置**：`_factors_from_point` 函数
- **问题描述**：
  ```python
  if p.image_source is not None:
      factors["image_source"] = 0.0  # 字符串，AI 端用默认处理
  if p.land_use_type is not None:
      factors["land_use_type"] = 0.0  # 字符串
  ```
  当 MonitoringPoint 中存在字符串类型字段时，代码将它们设为 float `0.0` 而不是字符串原值。导致：
  1. `score_terrain` 中 `geology_label` 读到 `0.0` 而不是字符串
  2. `score_historical` 中 `land_use` 得到 `"0.0"` 而不是土地利用类型
- **影响**：批量检测和区域检测中的图像来源和土地利用类型信息完全丢失
- **修复方案**：直接将字符串原值存入 factors 字典，由各评分函数自行处理类型转换

### HIGH-3 AI 融合评分只升级预警等级不降级，导致预警虚高

- **文件**：`backend/src/main/java/cn/disasterguard/warning/engine/WarningCreateService.java`
- **问题描述**：
  AI 融合评分的逻辑是只能升级（CRITICAL→红, HIGH→橙, MEDIUM→黄），不能降级。
  如果规则引擎因为某个指标瞬时超阈值触发了橙色预警，但 AI 综合评估实际为 LOW，预警依然是橙色。
- **影响**：可能产生大量高等级误报，导致"狼来了"效应
- **修复方案**：增加降级逻辑（AI 评估低于规则等级且差距较大时降级），或增加置信度阈值控制

### HIGH-10 活跃维度≤3 时回退 v1 模式，v2 七维度权重未被使用

- **文件**：`ai-service/app/models/lstm_model.py`
- **问题描述**：
  LSTM 模型 `output_size=7`，固定输出 7 步预测。当 `horizon > 7` 时，只用 7 个预测点的首尾差算一个线性趋势，然后做简单线性外推。
  前端 `DisasterForecastPage` 最高支持 72 小时预测，远超模型能力。
- **影响**：超过 7 步的预测结果精度极低，基本是"画直线"，可能误导用户
- **修复方案**：限制 horizon 最大值为 7，或实现真正的多步滚动预测（自回归生成）

## 四、中等缺陷（MEDIUM）

### MEDIUM-1 社媒位置聚类逻辑过于简化，结果无实际意义

- **文件**：`ai-service/app/routers/social_media.py`
- **问题描述**：
  对于文本类型的位置，只用前 10 个字符作为聚类 key。"龙安镇青龙村一组"和"龙安镇青龙村二组"会被聚在一起，而"青龙村"和"龙安镇青龙村"不会被聚在一起。
- **影响**：位置聚类结果不可靠，无法用于实际的灾害区域研判

---

### MEDIUM-2 经纬度正则表达式可能误匹配非坐标数字

- **文件**：`ai-service/app/routers/social_media.py`
- **问题描述**：
  正则 `(\d+\.?\d*)[°,]\s*(\d+\.?\d*)[°NSE]` 可能误匹配中文文本中的数字对（如"降雨量100.5, 水位2.3米"）。
- **影响**：社媒分析的位置提取可能产生错误的经纬度

---

### MEDIUM-3 预警等级映射存在中英文体系混用风险

- **文件**：`backend/src/main/java/cn/disasterguard/warning/engine/AiWarningScheduler.java`
- **问题描述**：
  AI 联动预警使用中文预警等级（"红色预警"），而前端人工发布预警使用英文码（`red/orange/yellow/blue`），经过 `WarningService.normalizeLevel` 转换为中文。这种双轨制存在不一致风险。
- **影响**：不同来源的预警等级格式可能不一致

---

### MEDIUM-4 批量刷新方法使用 @Transactional，长事务风险高

- **文件**：`backend/src/main/java/cn/disasterguard/ai/service/AiInsightService.java`
- **问题描述**：
  `refreshAll` 方法标注了 `@Transactional`，但内部循环遍历所有灾害点并逐一调用 AI 服务进行 HTTP 推理。如果有 100 个灾害点，事务可能持续 10 秒以上。
- **影响**：高并发下数据库连接池耗尽，可能导致其他业务操作超时

---

### MEDIUM-5 预警详情页使用已过时的 fusionRiskAuto 接口

- **文件**：`frontend/src/views/warning/WarningDetailPage.vue`
- **问题描述**：
  预警详情页使用 `fusionRiskAuto` 获取 AI 风险，但项目中已经有更全面的 `disasterAssessment` 接口（返回三维度明细 + 灾害类型 + 推理链）。
- **影响**：预警详情页展示的 AI 风险信息过于简略

### MEDIUM-6 前端 sentinelService 取消任务 URL 路径错误

- **文件**：`frontend/src/services/_architecture/core/sentinelService.js`
- **位置**：第 148 行
- **问题描述**：

  ```javascript
  const url = `${DEFAULT_AI_SERVICE_BASE}${STATUS_PATH(jobId)}/cancel`
  ```
  `STATUS_PATH(jobId)` 返回 `/sentinel/jobs/{jobId}`，拼接后变成 `/sentinel/jobs/{jobId}/cancel`。

  但如果前端走 Java 网关，Java 端没有这个端点（见 CRITICAL-2）。
- **影响**：走 Java 网关路线时取消功能不可用

### MEDIUM-7 CDSE 凭证未配置时错误信息不友好

- **文件**：`ai-service/app/utils/cdse_token.py`
- **问题描述**：

### MEDIUM-8 卫星差异计算的热点聚类精度低

### MEDIUM-9 卫星合成任务存储在内存中，重启丢失

## 八、总结

本项目存在 **42 个已知问题**，其中 **10 个致命缺陷**直接导致核心功能不可用：

1. **卫星地图功能**：前端绕过认证直连 AI 服务 + Java 后端无转发接口 + file:// URL 无法加载 → **用户完全无法使用卫星地图**
2. **AI 实时监测**：异常检测数据格式不匹配 + 融合评分多乘 100 倍 + 基于模拟天气数据 → **监测结果完全错误**
3. **AI 分析**：自适应归一化失效 + 多模态全是 Mock + 社媒等级偏差 + 维度回退 → **分析结果不可靠**
4. **预警报告**：红色预警显示为蓝色 + 报告生成是空壳 + 只升级不降级 → **预警和报告完全不可信**
5. **API 接入**：多处前端直连 AI 服务绕过认证 + 数据格式不匹配 → **架构一致性被破坏**

建议按照 P0 → P1 → P2 → P3 的顺序逐步修复，优先解决导致功能完全不可用的致命缺陷。
