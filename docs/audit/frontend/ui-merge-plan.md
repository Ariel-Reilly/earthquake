# DisasterGuard 前端界面合并优化方案

**版本**: v1.0
**日期**: 2026-10-03
**现状**: 44 个独立页面 → **优化后**: 约 22 个核心页面（减少 50%）

---

## 一、问题分析

### 1.1 现状

当前前端共有 **44 个独立页面**，分布在 5 个导航分组中：

| 导航分组 | 页面数量 | 典型问题 |
|---------|---------|---------|
| 监测与态势 | 4 个 | 多个地图页面功能重叠（实时地图/设备地图/气象/卫星） |
| AI 与事件 | 13 个 | 拆分最细，AI 相关页面多达 7 个，用户需频繁跳转 |
| 预警与处置 | 7 个 | 资源调度、路径规划、应急事件业务强关联但分散 |
| 数据与模型 | 6 个 | 数据源、同步、目录是同一领域的三个侧面 |
| 系统与统计 | 14 个 | 设置类页面过度拆分（系统设置/账号安全/个人中心） |

### 1.2 核心问题

1. **导航层级过深**：用户在相关功能间切换需要反复回到侧边栏跳转
2. **功能重复建设**：设备轨迹回放在 2 个页面各实现了一套；个人设置在 3 个页面重复
3. **操作割裂**：应急处置流程中，资源调度和路径规划本是连续动作，却分成两个页面
4. **认知负担重**：40+ 菜单项让新用户难以快速找到所需功能

### 1.3 优化目标

- 页面数量从 **44 → ~22**（减少 50%）
- 导航分组从 **5 → 4**（更聚焦的业务域）
- 强关联功能通过 **Tab / 抽屉 / 分步流程** 整合在同一页面
- 减少 60% 的跨页面跳转

## 三、详细合并方案

### 3.1 监测态势域（4页 → 3页）

#### 合并 1：监测地图（整合 4 个地图页面）

**合并前**（4 个独立页面）：
- `RealTimeMapPage` — 实时监测地图
- `DeviceMapPage` — 设备地图与轨迹回放
- `WeatherPage` — 气象分析
- `SatelliteComparePage` — 时相对比卫星影像

**合并后**（1 个页面 + 图层/模式切换）：

```
┌─────────────────────────────────────────────────────────┐
│  监测地图                                                │
├─────────────────────────────────────────────────────────┤
│  [实时监测] [设备分布] [气象叠加] [卫星对比]    ← 顶部Tab │
├─────────────────────────────────────────────────────────┤
│                                                         │
│                    地图主视图                            │
│                                                         │
├─────────────────────────────────────────────────────────┤
│  左侧：图层控制面板（灾害点/设备/预警/AI监测/气象图层）  │
│  右侧：详情抽屉（点击地图元素后展开）                    │
└─────────────────────────────────────────────────────────┘
```

**合并理由**：
- 4 个页面本质上都是「地图 + 不同图层」，只是底图和叠加数据不同
- 用户在实际使用中需要同时查看多种图层（如：灾害点 + 设备位置 + 气象）
- 现有实现中设备轨迹回放功能重复

**实现方式**：
- Tab 1「实时监测」：灾害点 + 预警 + AI 监测图层（原 RealTimeMapPage 核心）
- Tab 2「设备分布」：设备点位 + 轨迹回放（原 DeviceMapPage 核心）
- Tab 3「气象叠加」：气象雷达/卫星云图图层（原 WeatherPage 核心）
- Tab 4「卫星对比」：时相对比 + 变化检测（原 SatelliteComparePage 核心）

### 3.2 事件中心域（13页 → 5页）

#### 合并 2：事件工作台（整合 4 个事件相关页面）

**合并前**（4 个独立页面）：
- `HazardsListPage` — 灾害事件列表
- `EventCenterPage` — 统一事件中心
- `ConfirmationWorkbenchPage` — 人工确认工作台
- `ConfirmationSignPage` — 会签与转派

**合并后**（1 个页面 + Tab + 状态筛选）：

```
┌─────────────────────────────────────────────────────────┐
│  事件工作台                                [新建事件]    │
├─────────────────────────────────────────────────────────┤
│  [全部事件] [待确认] [会签中] [已闭环]          ← 状态Tab │
├─────────────────────────────────────────────────────────┤
│  筛选：灾种 | 等级 | 时间 | 区域 | 负责人                │
├─────────────────────────────────────────────────────────┤
│  事件列表（左侧）          │  事件详情（右侧抽屉）       │
│  - HZ-001 青龙坡滑坡      │  ┌──────────────────────┐   │
│    状态：待确认 · 高风险   │  │ 基本信息             │   │
│  - HZ-002 大岭村崩塌      │  │ 时序数据/图表        │   │
│    状态：会签中 · 橙色     │  │ AI分析结果           │   │
│  - ...                    │  │ 操作：认领/确认/会签  │   │
│                           │  └──────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**合并理由**：
- 4 个页面都是围绕「事件」的不同状态视图，本质是同一个列表的不同筛选
- 用户的操作路径是：发现事件 → 确认 → 会签 → 闭环，本应是连贯流程
- 当前每个页面都有自己的列表+详情，代码重复度高

**状态 Tab 对应关系**：
- 「全部事件」= 原 HazardsListPage + EventCenterPage 合并
- 「待确认」= 原 ConfirmationWorkbenchPage（AI 生成的待人工确认事件）
- 「会签中」= 原 ConfirmationSignPage（需要专家会签的事件）
- 「已闭环」= 历史归档的事件

### 3.3 预警处置域（7页 → 4页）

#### 合并 5：应急指挥工作台（整合 3 个页面）

**合并前**（3 个独立页面）：
- `EmergencyPage` — 应急事件
- `ResourceDispatchPage` — 资源调度指挥
- `RoutePlanningPage` — 灾区路径规划

**合并后**（1 个页面 + 分步流程/面板）：

```
┌─────────────────────────────────────────────────────────┐
│  应急指挥工作台                             事件：HZ-001 │
├─────────────────────────────────────────────────────────┤
│  ○ 事件信息 → ○ 资源调度 → ○ 路径规划 → ○ 下达指令       │  ← 流程步骤
├─────────────────────────────────────────────────────────┤
│                                                         │
│  左侧：资源列表面板                                      │
│  - 救援队（3支）                                         │
│  - 物资库（5个）                                         │
│  - 医疗点（2个）                                         │
│                                                         │
│  中间：地图视图                                          │
│  灾害点 + 资源位置 + 规划路径                            │
│                                                         │
│  右侧：路径方案对比                                      │
│  ┌─最快路线─┐ ┌─最安全路线─┐ ┌─最短路线─┐              │
│  │ 2.3km    │ │ 3.1km     │ │ 2.8km   │              │
│  │ 12分钟   │ │ 18分钟    │ │ 15分钟  │              │
│  └─────────┘ └───────────┘ └─────────┘              │
│                                                         │
│                              [确认调度方案] [下达指令]   │
└─────────────────────────────────────────────────────────┘
```

**合并理由**：
- 资源调度和路径规划是应急处置的连续流程，分开会打断操作节奏
- 路径规划的起点/终点就是资源调度中选择的资源点和灾害点
- 合并后用户可以在同一个界面完成「选资源 → 规划路径 → 下达指令」

## 七、架构层面改进建议

### 7.1 通用布局组件

当前很多页面都是「列表 + 详情抽屉」模式，但每个页面都自己实现了一套。建议抽出通用组件：

```
<PageLayout
  title="页面标题"
  :actions="[ { label: '新建', onClick: handleCreate } ]"
>
  <template #sidebar>
    <!-- 左侧筛选/列表 -->
  </template>
  <template #default>
    <!-- 主内容区 -->
  </template>
  <template #drawer>
    <!-- 右侧详情抽屉 -->
  </template>
</PageLayout>
```

### 7.2 通用地图容器

当前 3 个地图页面（实时/设备/气象）各实现了一套 OpenLayers 初始化逻辑，建议抽出：

```
<MapContainer
  :center="[107.21, 30.61]"
  :zoom="12"
  :layers="['hazard', 'device', 'weather']"
  @feature-click="handleFeatureClick"
/>
```

### 7.3 统一 Tab 组件样式

当前各页面 Tab 样式不统一（有的胶囊、有的下划线、有的左侧竖排），建议统一设计语言。

### 7.4 路由保留与兼容

合并页面后，旧路由应保留并重定向到新页面，避免书签/链接失效：

```js
// 旧路由重定向
{ path: '/dashboard/message-center', redirect: '/dashboard/workbench' },
{ path: '/dashboard/todo', redirect: '/dashboard/workbench' },
{ path: '/dashboard/approvals', redirect: '/dashboard/workbench' },
// ...
```
