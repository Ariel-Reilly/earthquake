# 御灾智巡 · 项目文件结构梳理报告

> DisasterGuard v1.7.0 ｜ 梳理日期：2026-10-24
> 方式：全量目录扫描 + 文档比对 + git 索引核对（只读，未改动任何文件）
> 统计口径：源码文件数均**排除** `node_modules` / `.venv` / `target` / `dist` / `.npmcache` / `__pycache__` / 日志

---

## 一、结论先行

项目是 **4 个可独立部署模块 + 1 套基础设施 + 1 套运维脚本** 的多模块单体仓库，业务源码结构清晰、分层规范（后端 31 个业务包、前端 11 个业务域目录、AI 服务 16 个路由）。

主要问题不在源码，而在**源码之外的三类堆积**：

1. 根目录混入 **9 个非源码目录（约 44.7 MB）+ 19 个散置文件**，其中绝大部分与本项目无关；
2. `_out` / `_pdf` / `_work` / `.workbuddy` / 根 `package.json` 属于**另一个项目（智能拐杖管理系统）的毕设文档产出链**，残留在本仓库；
3. `README.md` 与 `docs/ARCHITECTURE.md` 的"项目结构"章节已与代码**明显漂移**（旧目录名、路由/页面计数、空目录）。

## 三、模块内部结构

### 3.1 backend（`cn.disasterguard.*`，31 包 / 328 java / 49 Controller）

按文件数降序（=实际复杂度分布）：

```
auth 44 · ai 37 · notification 29 · device 28 · common 19 · warning 18
ruleengine 17 · config 17 · emergency 15 · event 13 · governance 9 · inspection 9
report 7 · backup 7 · dashboard 6 · hazard 6 · task 6 · weather 5 · attachment 5
realtime 4 · audit 4 · system 3 · health 2 · region 2
todo 1 · confirmation 1 · analytics 1 · approval 1 · debug 1 · aop 1 · personnel 1
```

- **包结构本身健康**：`common`(19) + `config`(17) 承担基类/异常/权限/导出，业务包按域划分，与 `docs/ARCHITECTURE.md` §3.2 一致。
- **注意**：`hazard` 仅 6 个文件却是核心业务域，实际逻辑分散在 `event`(13)、`confirmation`(1)、`inspection`(9) 中——v1.7 统一事件中心迁移后包边界有残留。
- **资源层**：`application.yml`(7.3 KB) + dev/docker/prod 三 profile + `schema.sql`(80 KB) + `data.sql`(75 KB，含 7 个种子账号)。
- **测试薄弱**：`src/test` 仅 8 个 java 文件（占主源码 2.4%），CI 只做 `mvn test-compile`（编译测试，不跑测试）。
- **`backend/` 根散置 22 个文件 / 1.8 MB**：6 份 SMS 文档 + 10 个 SMS 诊断脚本（`DIAGNOSE_SMS.ps1` 16.4 KB、`RUN_ALL_SMS_DIAGNOSTICS.ps1` 12.4 KB 等）+ `FILE_SUMMARY.md` + `boot.log`(1.6 MB) + `backend.log`(96.8 KB) + `.env.local`、`.tmp-verify/`、`.idea/`、`logs/`、`target/`。

### 3.2 frontend（`src/` 为标准 SPA 分层）

```
src/
├── views/          63 个 .vue
│   ├── system 15 · warning 9 · ai 8 · monitor 6 · hazard 6 · data 5
│   ├── settings 3 · device 3 · mobile 1 · screen 1 · profile 0（空）
│   └── 根级 6：Welcome 145KB · Overview 105KB · Register 36KB · AdminApplications 17KB · 403 · 500
├── components/     43 个 .vue（base/common/confirmation/event/layout/navigation/
```

- **分层设计合理**：`services/_architecture/core`（技术通用）与 `domain`（业务）分离，`dashboardApi.js` 作聚合出口，`services/README.md` 有说明。
- **过渡态未收尾**：根级 `aiApi.js`(50 B)、`mapService.js`(53 B)、`realtimeService.js`(155 B)、`satelliteCompareService.js`(68 B)、`sentinelService.js`(58 B) 是纯 re-export 薄层，新旧入口并存。
- **`src/.env` 与 `src/services/README.md` 同层混放**：源码目录里有 env 文件（已忽略，但位置不规范）。
- **工程化完整**：eslint / prettier / stylelint / knip + `frontend/scripts/` 下 10 个 `check:*` / `tokenize:*` / `repair:*` 校验脚本，并接入 CI。

- `app/README.md` 声称"自包含部署、模型配置脚本全在 ai-service 内"，与实际一致。

## 六、建议的整理动作（仅为方案，未执行）

- 注意 `docs/` 里还混有 3 份"御灾智巡"毕设 docx 与 `README.md.bak` —— 建议单独归入 `docs/graduation/`。

### P1 · 清理模块内的旧形态

- `ai-service/web.py` + `ai.py`：确认无外部调用方后归档（建议 `ai-service/_archive/`），或在 `README.md` 明确三者定位与启动方式。
- `backend/` 根 22 个散置文件：SMS 文档 → `docs/guides/`，SMS 诊断脚本 → `scripts/`，`boot.log`/`backend.log`/`logs/`/`.tmp-verify/` → 保持忽略并可删除。
- 3 个空目录：`frontend/src/components/base`、`frontend/src/components/notification`、`frontend/src/views/profile`。

### P2 · 结构优化（需要改动源码，按 `.cursorrules`"严禁跨模块修改"逐模块推进）

1. **修正文档**：更新 `README.md` §项目结构与页面/路由计数，`docs/ARCHITECTURE.md` §3.1 去掉 `profile` 空目录并补 `RegisterPage`/`AdminApplicationsPage`；把根 `UX-Audit-Report.md` 改名并入 `docs/audit/`。

6. **沙盘产出归档**：`examples/` 7 组产出中带 `.ifc/.obj` 的 5 组高度重复，建议保留 1 套权威版 + `tools/build_*.py` 生成脚本，其余删除。
