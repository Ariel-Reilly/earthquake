## 一、发布阻断项（P0，已修并实测）

### 1. 后端连不上数据库，服务起不来

- **现象**：`spring-boot:run` 启动即失败。
- **真实报错**：
  ```
  org.postgresql.util.PSQLException: FATAL: password authentication failed for user "disasterguard"
  → DataSourceInitializationConfiguration: Failed to execute database script
  ```
- **根因**：`.env` 里的 `POSTGRES_PASSWORD` 与运行中的 `disasterguard-postgres` 容器**实际库密码不一致**。  
  容器数据卷是早期初始化的，后来 compose / `.env` 改过密码，但 PostgreSQL 不会因为环境变量变化  
  去改已有角色密码，属于典型配置漂移。
- **修复**：以 `.env` 为唯一真源，在容器内执行 `ALTER USER disasterguard WITH PASSWORD :'pw'`。  
  未改任何业务数据，未重建数据卷。
- **验证**：
  ```
  PGPASSWORD=$PW psql -h 127.0.0.1 -p 15432 -U disasterguard -d disasterguard
  → connected|7        （warning_event 7 行，可查询）
  后端 /api/health → HTTP 403（服务已监听，鉴权生效）
  ```
- **发布注意**：新环境必须保证 `POSTGRES_PASSWORD` 与数据卷初始化时一致，否则同样起不来。  
  建议首次部署用**空数据卷**，或部署后执行一次密码对齐。

### 2. 登录账号与文档不符

- **事实**：`data.sql:8` 注明测试账号密码为 `admin123`；部署文档/历史笔记里的 `123456` 已失效。
- **影响**：按旧密码登录返回 `401 用户名或密码错误`，会被误判成鉴权故障。
- **验证**：`admin / admin123` → `{"code":0,"message":"登录成功", ...}`。

## 二、核心功能造假（P1，已修并实测）

### 3. 灾害点预警是“假”的：规则全部被跳过

- **根因（双重）**：
  1. 6 条预警规则的 `metric_code` 是复合标签（`rainfall_24h_slope`、`crack_width_rain` 等），  
     `device_metric` 表里**根本不存在**这些码；
  2. `RuleEngineScheduler` 有一道前置门禁 `if (!metrics.containsKey(rule.getMetricCode())) continue;`，  
     于是每 30 秒一轮、每轮 6 条规则全部 `continue`，**预警链路从未自动产生过预警**，  
     页面上看到的预警都来自 `data.sql` 种子数据。
- **修复**：
  - `WarningRuleEvaluator` 支持 `A > x AND B > y` 复合表达式与“右侧引用指标名”，  
    无法判定的条件（如字符串 `OFFLINE`）返回空，**不猜、不误报**；
  - 删除调度器的 metric_code 前置门禁，是否命中统一交给表达式求值；
  - 规则主指标对齐真实上报的 `device_metric.metric_code`。
- **实测结果**（重启后端后等一轮 cron）：
  ```
  WG-9367089B | R001 | HZ-004 | 黄色预警 | rainfall_24h=80.0
  WG-652B8815 | R004 | HZ-002 | 蓝色预警 | tilt_angle=3.8
  WG-61F3B953 | R005 | HZ-004 | 黄色预警 | displacement_rate=6.0
  ```
  触发值与表达式、真实指标完全对得上，且与已有未关闭预警的组合不重复生成。

### 4. 规则“能跑了”但语义是错的（上一轮引入的假修复，已纠正）

- **问题**：为了让规则出预警，曾把 R004“设备离线告警”写成 `tilt_angle > 3`、  
  R005“地震触发巡检”写成 `displacement_rate > 5`，**名称与表达式不一致**，  
  等于用错规则发预警。且 `ON CONFLICT DO UPDATE` 漏了 `rule_name`，库里名称仍是旧的。
- **修复**：规则名、主指标、表达式、备注统一为真实语义，`DO UPDATE` 补上 `rule_name`。  
  无数据源的两类规则（设备在线状态、地震震级）在备注中写明为何改判维度。
- **当前规则表**（真实库）：
  | 规则   | 名称             | 表达式                                            |
  | ---- | -------------- | ---------------------------------------------- |
  | R001 | 滑坡黄色预警（24h 雨量） | `rainfall_24h > 50`                            |
  | R002 | 滑坡橙色预警（雨量+位移）  | `rainfall_24h > 80 AND displacement_rate > 5`  |
  | R003 | 洪水红色预警（水位）     | `water_level > 25`                             |
  | R004 | 倾角异常蓝色预警       | `tilt_angle > 3`                               |
  | R005 | 位移速率黄色预警       | `displacement_rate > 5`                        |
  | R006 | 崩塌黄色预警（裂缝扩展）   | `crack_width_rate > 2.0 AND rainfall_24h > 30` |

### 5. “AI 识别结果”页整页造假

- **证据**（`frontend/src/views/ai/AiResultsPage.vue`）：
  - `confidence: h.confidence ?? 0.6 + Math.random() * 0.3`
  - 4 个模型投票（YOLOv8 / LSTM / XGBoost / InSAR）分数全部 `Math.random()`
  - “多源证据”三条中文文案写死
  - “转人工确认”“误报”只 `emit('notify', '已推送…')` 后在本地删卡片，**没有任何后端请求**
- **修复**：改为渲染后端 `HazardDto` 的真实字段  
  （`detectionConfidence` / `aiScore` / `aiLevelLabel` / `aiDisasterType` / `aiAnalyzedAt` /  
  `aiDeviceAvailable` / `eventCode` / `eventState`），缺字段显示“—”或“未评估”；  
  删除虚构的模型投票与证据块；两个写操作改为真实调用。
- **验证**：`GET /api/hazards/ai-monitor` 真实返回  
  `detectionConfidence: 0.86, aiScore: 16.09, aiLevelLabel: "低风险", eventState: "DETECTED"`。

### 6. 该关联的地方没关联：AI 结果 → 确认队列

- **断点**：AI 识别出的灾害点无法真正进入确认队列，按钮只是本地消失。
- **新增端点**（`HazardController` / `HazardService`）：
  - `POST /api/hazards/{hazardCode}/submit-confirmation`  
    按 `unified_event` 队列口径（`state ∈ {DETECTED, CONFIRMING}`）返回是否在队列；  
    不新建重复事件、不把已确认事件倒退回待确认。
  - `POST /api/hazards/{hazardCode}/dismiss`  
    误报归档走状态机 `DISMISS → CLOSED`，原因必填；已发布预警 / 应急中的事件拒绝误报归档。
  - 操作人取 `Authentication#getName()`，不信任请求体。
- **实测**：
  ```
  POST HZ-001/submit-confirmation → {"state":"DETECTED","alreadyInQueue":true,"message":"已在人工确认队列"}
  POST HZ-001/dismiss  {}         → {"code":400,"message":"请填写误报原因"}
  POST HZ-999/...                 → {"code":404,"message":"未找到灾害点：HZ-999"}
  ```

### 7. 规则试算“永远不满足”：前后端参数契约错位

- **根因**：前端把 `inputData` 放在请求体，后端签名是  
  `@RequestBody RuleTestRequest` + `@RequestParam Map inputData`，后端恒收到空 Map。
- **修复**：改为从 `RuleTestRequest#inputData()` 取，与前端契约一致。
- **同时**：`RuleTestPanel` 的 catch 分支不再把本地演算结果冒充后端结果，  
  而是标注“后端规则引擎调用失败，以下为前端本地预演，未经过后端规则引擎”。

## 三、地图（用户点名项）

### 8. 卫星底图：从“经常合成失败”改为真实瓦片金字塔

- **原实现**：底图依赖 Sentinel-1 + Sentinel-2 在线合成，合成任务走外部数据源，  
  失败即白屏；矢量底图为 OSM（境外源，中国境内不合规）。
- **现实现**（`mapService.js`）：
  - 主影像：高德卫星影像瓦片 `webst0{1..4}.is.autonavi.com/appmaptile?style=6`，  
    zoom 3–19，无需合成任务、无需 key；
  - 备源：天地图 `img_w`（配置 `VITE_TDT_TOKEN` 后启用），故障时自动切换；
  - 全部点位按 `satelliteDatum = gcj02` 投影，切备源时整体重投影为 `wgs84`，避免 100–500m 系统性偏移；
  - 前端已无 `openstreetmap` / `arcgisonline` / `mapbox` / `google` 瓦片残留（grep 为 0）。
- **实测**：高德 `style=6` 瓦片 HTTP 200；天地图无 tk 时返回鉴权错误（已按备源降级处理）。
- **UI**：OverviewPage 的“合成卫星”按钮与进度条已移除，改为“卫星/影像”直接切换；  
  实时地图的“地形”选项已移除（没有地形数据源，留着就是假的）。

## 四、AI 训练数据（用户点名项）

### 9. 真相与整改

| 项          | 实测结论                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 模型权重       | **真实存在**：`yolo_crack.onnx` 13MB、`xgboost_fusion.json` 3.7MB、`lstm_displacement.pt`、`isolation_forest.joblib` |
| 训练脚本       | 8 个，齐全（`scripts/training/`）                                                                                  |
| 训练数据       | **合成**：`train_comprehensive_v2.py` 的 `synthesize_sample()` 用 `random` 生成 8800 条样本                            |
| “真实反馈”     | **伪**：`_load_feedback_rows` 用 `predicted_score` 反推 7 维特征，等于把模型输出当输入                                          |
| 反馈存储       | **内存 deque**，进程重启即丢失，攒不出训练集                                                                                  |
| YOLO 裂缝数据集 | **原先不存在**；**本轮已建** `datasets/disaster-v1`（767 图 / 1263 实例 / 2 类，全部为公开人工标注）     |
| YOLO 权重真实性 | **假**：`yolo_crack.onnx` 输出 `[1,84,8400]` = 4+80 类，实为 COCO 通用模型，对真实裂缝图输出 0 框           |

已整改：

1. `FeedbackStore` 增加 **JSONL 落盘**（`models/feedback/feedback.jsonl`，可用 `AI_FEEDBACK_DIR` 挂卷），  
   启动自动回读，人工复核结论不再随重启消失。
2. `_load_feedback_rows` **删除 score 反推**：只有带 `factors`（真实指标快照）的反馈进训练集，  
   其余跳过并计数。
3. `train_xgboost` 新增 `allow_synthetic`（默认 `False`），训练结果带 `dataset`  
   （`real_samples` / `skipped_no_features` / `synthetic_ratio`），对外展示指标时必须连带这组数据。
4. `POST /api/ai/model/retrain` 的样本判断从“反馈总条数”改为“可训练样本数”，  
   不足时明确返回还差多少条、以及“需附带 factors”的提示。
5. 后端 `POST /api/ai/feedback` 在未传 `factors` 时，**自动按 hazardCode 从 `device_metric`  
   取各指标最新值填充**，让复核结论真正沉淀为训练样本。
6. **新建真实标注数据集 `ai-service/datasets/disaster-v1`**：3 个公开人工标注源（Roboflow 裂缝 COCO
   实例分割 433 图；Zenodo 尼泊尔滑坡 230 图、意大利滑坡 104 图，均 CC-BY-4.0），767 图 / 1263 实例 / 2 类。
   转换脚本只做几何映射（bbox 线性换算、掩码连通域外接矩形），不生成图像、不生成标注、不含模型预测。
   内置源内去重 + 跨划分去重（Nepal 官方 Val 与 Train 有 33/35 内容重复，已弃用其原始划分）。
   校验：图像标签配对 767/767、坐标与类别全部合法、跨 split 泄漏 0。详见 `datasets/disaster-v1/DATASET_CARD.md`。
7. **`yolo_crack.onnx` 的真实身份已查明并处置**：输出 84 类 = COCO 通用模型，文件名却是 crack。
   现按 onnxruntime 输出维度判定，COCO 模型加载即告警（`model_variant=yolov8n-coco`），
   `routers/detection.py` 对非业务模型**一律返回 `disasterType=none`**，不再把"检出任意目标"映射成
   "泥石流"（旧逻辑写死 `BUSINESS_DISASTER_TYPE="debris_flow"`、置信度 0.88，已删）。
8. **`CLASSES` 从虚构的 5 类收敛为真实覆盖的 2 类**（crack / landslide）。原
   `[crack, rockfall, slump, debris, normal]` 中后三类没有任何标注数据支撑，属虚报能力。

**已实测的完整训练链路**（3 epoch 冒烟，CPU 8 分钟）：数据加载 590 train / 106 val 正常、30 张背景图被正确识别为空标签、
训练收敛、导出 ONNX 输出 `[1,6,8400]`、检测器判为业务模型 `num_classes=2`、对真实裂缝图输出 `crack` 0.93/0.63/0.57。
mAP50 = 0.121（crack 0.22 / landslide 0.022），**仅证明能训，不构成可用模型**。

**结论**：现在有真实标注数据集、有可复现的构建与校验脚本、有跑通的训练链路；  
但没有"已用真实数据训练好的可用模型"——那需要 50–100 epoch，本轮未做，也不做此表述。
